During sandbox refreshes, the following things are not copied from production:

-   **Websites and web store domains**
    
    Domains are not copied from your production account to your sandbox. After a sandbox refresh, you must set up domains in the sandbox. If you have multiple sandboxes, ensure that across all of your sandboxes, the domains are unique. An error message is generated if there are duplicate domains. See [Manual Certificates](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N2485854.html) and [Set Up Domains for Web Stores](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N2484898.html) for more information.
    
-   **Hard-coded Link Behavior**
    
    Neither internal nor external hard-coded links are modified during sandbox refreshes. Use supported dynamic tags or placeholders to generate links that resolve to the corresponding environment.
    
    For more information about Web Site Tags, see [Tags for Use in HTML Pages and Site Templates](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N2630406.html).
    
-   **Customer Center role assignments for customer users**
    
    Customer Center role assignments for customer users are not copied from production accounts to sandboxes during refreshes. Due to this limitation, customer login functionality does not work in sandbox after a refresh, even if it has been working in the production account. If you want to set up this functionality to work in sandbox, you can do a CSV import of customer records into the sandbox, to set passwords and Give Access to True for customer users.
    
    For more information, see [CSV Imports](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/book_4470700566.html).
    
-   **SAML configuration**
    
    SAML configuration is not copied from the production account to the sandbox. For details, see [SAML SSO in Multiple NetSuite Account Types](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/bridgehead_4430963939.html).
    
    Note:
    
    It can happen that the configuration gets copied to your sandbox after refresh. However, you should always configure SAML in your sandbox again, because there is no guarantee that the copied configuration works correctly.
    
-   **System notes on records**
    
    System notes are not copied from the production account to the sandbox. For more information about system notes, see [System Notes Overview](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_158644279544.html).
    
-   **Deleted Records**
    
    Deleted records aren't copied from the production account to the sandbox. For information about deleted records, see [Searching for Deleted Records](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4031815869.html)
    
-   **SuiteFlow (workflow) history logs**
    
    SuiteFlow (workflow) history logs are not copied from the production account to the sandbox. For more information, see [SuiteFlow Overview](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_4068260113.html) and [Workflow History Subtab](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4471798307.html). Workflow instances are not copied from the production account to the sandbox either.
    
-   **Token-based Authentication (TBA)**
    
    Tokens created in your production account are not copied to your sandbox during a refresh. To test token-based authentication in your sandbox, you must create tokens in that sandbox. Each time your sandbox is refreshed, you will need to create new tokens in the sandbox. For information about creating tokens, see [Manage TBA Tokens in the NetSuite UI](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4254975694.html).
    
-   **OAuth 2.0**
    
    Applications authorized using the OAuth 2.0 feature in your NetSuite production account are not copied to your Release Preview or to your sandbox accounts. Users must authorize applications explicitly in Release Preview or in a sandbox to test OAuth 2.0 feature in these accounts. Each time the sandbox is refreshed, users must authorize applications explicitly in the sandbox. For more information about OAuth 2.0 Authorized Applications, see [Managing OAuth 2.0 Authorized Applications](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_157771979135.html).
    
-   **Eliminate Intercompany Transactions**
    
    The Eliminate Intercompany Transaction tasks are not copied from production to sandbox accounts. This means the Eliminate Intercompany Transactions task status results only appear in the account in which the tasks are run, and may not be the same in your production and sandbox accounts. For more information, see [Viewing Intercompany Elimination Results](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/bridgehead_N1501917.html).
    
-   **Campaign response history**
    
    Campaign response history is not copied from production to sandbox accounts. For more information about campaign response history, see [Campaign Response Summary Report](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1012638.html).
