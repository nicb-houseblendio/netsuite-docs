## What is Builder Kit {#subsect_0423105723}

You can use the Electronic Invoicing Builder Kit feature to meet the e-invoicing compliance requirements in countries supported by Avalara, and where NetSuite does not provide a localization support at present.

This enables you to use [Avalara for E-Invoicing](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_0319043032.html).

Important:

See [E- Invoicing Mandate Definitions](https://developer.avalara.com/elr-usecases/), for the list of e-invoicing mandates supported by Avalara.

Before using e-invoicing builder kit, ensure to check if your country is present in the list of countries with e-invoicing support provided by NetSuite.

## Understanding Builder Kit {#subsect_0423111259}

The Electronic Invoicing Builder kit enables you to implement the e-invoicing solution for your requirements. If the mandate is supported by Avalara, you can implement a working solution for it in your NetSuite account.

When you use Builder Kit to implement your e-invoicing solution, you set up following components:

-   For Outbound:
    
    -   E-Document Template (with custom data source)
        
    -   Outbound Extension Plugin
        
    -   Document status processing of a sent e-document (with custom processing logic).
        
    -   The Mandate definition- this enables you to fulfill a required mandate and own its implementation details.
        
-   For Inbound:
    
    E-Document Template (Custom Data source plugin implementation)- to process inbound e-documents that you receive through Avalara from networks like PEPPOL)
    

Note:

Outbound and Inbound can be set up independent to each other when you use Builder Kit to implement the e-invoicing solution.

After you implement the Builder Kit feature and the required local setup is completed, the standard E- Invoicing SuiteApp is ready. You must perform the following steps to use e-invoicing:

-   Generate e-documents for country mandate of your choice.
    
-   Send the document to networks like PEPPOL or tax authorities (supported by Avalara).
    
-   Sync the status of the same e-document back at NetSuite, after the e-document is sent on networks like PEPPOL or to tax authorities.
    
-   Receive and send transaction responses.
    

## Components of the Electronic Invoicing Builder Kit {#subsect_0423113252}

You should create and configure the following components of the Builder kit based on local requirements:

-   Mandate
    
-   E- Document Templates
    
-   Custom Plugin Implementations
    
    -   Custom Data Source for E-document (Outbound)
        
    -   Avalara Message Process Plugin Type
        
    -   Inbound Custom Data Source Plugin Type
        
-   Starter Templates:
    
    The Builder kit feature provides starter templates that you can customize further and then use in the Builder kit to tailor the e-invoicing solution to your desired country and e-invoicing mandates.
    
    The starter template include:
    
    -   Sample SuiteScript code for the custom plugin types. These can be used as a starting point and can be configured further.
        
    -   E-Document Templates (FreeMarker Templates to generate Generic PEPPOL e-documents) which can be configured to enable:
        
        -   Generation of a compliant e-document.
            
        -   Sending the e-document to the concerned Tax Authorities or networks like PEPPOL (powered by Avalara).
            
        -   Processing responses for tax authorities/Networks.
            

An additional step involved in the configuration of the Builder kit is creating the required [Custom Fields](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_N2826978.html) and/ or [Custom Records Overview](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_N2875173.html), for input and output values of the e-invoicing, depending on your mandate requirements. This is done using the standard NetSuite customization. For more information see, [Customization Overview](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_N2824008.html).

#### Create Plugin Implementation {#subsect_0423122039}

You must have the Administrator role to create the plugin implementations.

You can create plugin implementations of below types using the samples provided as part of EI SuiteApp:

-   Avalara Message Process Plugin Type- for document status processing.
    
    File cabinet path- SuiteApps > com.netsuite.electronicinvoicing > Sample Templates > Builder > pl\_starter\_avalara\_message\_process.js
    
-   Custom Data Source for E-document- for outbound generation.
    
    File cabinet path- SuiteApps > com.netsuite.electronicinvoicing > Sample Templates > Builder > pl\_starter\_generic\_outbound\_cds.js
    
-   Outbound Extension Plugin Implementation- for outbound generation
    
    File cabinet path- SuiteApps > com.netsuite.electronicinvoicing > Sample Templates > Builder > pl\_starter\_outbound\_extension.js
    
    For more information, see [Creating a Custom Plug-in Implementation for Extend E- Invoicing Plug-in](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_1027090818.html)
    
-   Inbound Custom Data Source Plugin Type- for inbound conversion.
    
    File cabinet path- SuiteApps > com.netsuite.electronicinvoicing > Sample Templates > Builder > pl\_starter\_generic\_inbound\_cds.js
    
-   Inbound Custom Data Source Plugin Type- (optional- implement this to override the default behavior of vendor identification that uses the Supplier Endpoint Identifier (Peppol ID) (EndpointID).
    
    File cabinet path- SuiteApps > com.netsuite.electronicinvoicing > Sample Templates > Builder > pl\_starter\_inbound\_cds\_resolve\_vendor.js
    

#### To use samples, you can perform the following steps to create and copy them:

1.  Go to File Cabinet > SuiteBundles > Bundle 436209 > com.netsuite.electronicinvoicing > Sample Templates > Builder > Plugin Implementations
    
2.  Download the Plugin Implementations folder. It gets downloaded as a zip file.
    
3.  You can now upload the zip into the file cabinet folder of your choice. Create a folder under File Cabinet > SuiteScripts called My Builder Scripts.
    
4.  Go to My Builder Scripts and upload the zip file using the "Advanced Add" option.
    
5.  After the upload, you can go to the files under the plugins folder and rename them as per your choice, for identification while using these files to create Plug-in Implementations.
    

You can refer to the already sourced Transaction data available from Electronic Invoicing (refer to CDS data available from EI). If you need to override the available values, you can do it when implementing. If it is not required to override, you don't need to take any action and the values will be used during e-document generation, depending on the template mappings. Refer to the CDS data available from reference Outbound UBL CDS and add the missing or tweak the existing if needed, based on countries' requirement.

For more details on how to create plugin implementation, see [Creating a Custom Plug-in Alternate Implementation](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_3987096698.html).

#### Creating E- Document Templates using Builder Kit {#subsect_0423010117}

You must have the Administrator role to create the e-document templates using Builder kit. You can use Builder Kit to create an E-Document Template with ready 'starter' details which can be customized according to your needs.

You will need e-document templates to generate e-documents. Builder Kit helps you create e-document templates with standard/starter mappings and the custom data sourcing implementation, that you can further customize according to your needs.

#### Steps to create the E-document templates:

1.  Go to Setup > E-Invoicing > Builder Kit
    
2.  Enter the required details:
    
    -   Name of the Builder E-Document Template.
        
    -   E-Document Package you want the Template to reside in.
        
    -   Subsidiaries you want the E-Document Template to be available for.
        
    -   Outbound Details
        
        1.  Outbound Template Starter - select the sample starting template with mappings.
            
        2.  Outbound CDS - select the sample plugin implementation that sources the transaction data. You can select the CDS plugin implementation type when you [Create Plugin Implementation](#subsect_0423122039).
            
        3.  Outbound Extension Plugin- select the plug-in Implementation from the dropdown list.
            
        4.  Apply Validations- check the box if validations are required to be triggered during e-document generation.
            
            For more information about validations, see [Apply Validations Enabled](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4629495887.html#bridgehead_0806021409)
            
    -   Inbound Details
        
        1.  Inbound Template Starter - You can select Inbound Generic PEPPOL. This provides the default mappings which can be used to convert a PEPPOL E- Document.
            
        2.  Inbound CDS - select the inbound custom data sourcing implementation.
            
        3.  Inbound XSD - It is preferred to set Inbound XSD. This helps auto assign this E-Document Template to the matching inbound XMLs. For more information, see [Understanding XSD in Inbound E-Document Templates](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_1116122715.html).
            
3.  Click **Save**.
    

You will be redirected to the created E-Document Template, with the 'Template for Outbound E- documents' and 'Custom Data Source Plugin Implementation' already populated, based on your selection of Outbound Starter and Outbound CDS.

Similarly, if you provided a choice for Inbound Starter, Inbound CDS, and Inbound XSD, the newly created E-Document Template record contains 'Field Mapping for Inbound E-documents' already populated, based on your selection.

You can always modify these field values in the created E-Document Template by navigating to the record by going to Setup > Electronic Invoicing > E-Document Templates.

#### Create the Required Custom Fields {#subsect_0423011839}

The country mandate or network to which the e-documents are sent (for example- PEPPOL) might require associated values to be stored with an invoice, before the e-document is generated and sent, and after the e-document is sent.

You may need to "create custom fields" depending on your country mandate. These custom fields could be used by you for two different purposes:

-   Values that should be stored before e-document generation, and to be used during e-document generation:
    
    A custom transaction body field can be used to store values that can be sourced and used in the generated e-document using Outbound CDS.
    
    For example: a value associated with the invoice, required to be present in the generated e-document.
    
-   Values that should be stored as result of sending out an e-document:
    
    Custom transaction body fields can be used store the results of sending the e-document to tax authority or networks like PEPPOL.
    
    For example: Unique ID of document generated by tax authority, digital signatures etc.

#### Sourcing custom data for e-documents {#subsect_0423020917}

You can include custom data in generated e-documents, by implementing Custom Data Source plugin implementation in SuiteScript and use them in the E-Document Templates. Builder Kit provides sample PEPPOL custom data source plugin implementation that can be used as a reference.

##### Understanding the Outbound CDS Plugin Implementation {#subsect_0423021046}

The Custom Data Source Plugin Implementation (CDS) is a custom plugin type that you can implement by creating plugin implementations. The plugin implementation you create should fully define the interface's function inject. It should contain the logic executed by an interface's function inject that will:

-   Return the data sourced using SuiteScript that is expected to be present in the generated e- document.
    
-   The Mandate that the document is being generated for.
    

More details about the interface:

| Functions |
| --- |
| inject(params) |

| Params |
| --- |
| {String} params.transactionId {Object} params.transactionRecord {Object} params.transactionDataCollection (optional) |

| Returns |
| --- |
| {Object} result {render.DataSource} result.alias {string} result.format {Object | Document | string} result.data {string} result.data.mandate {Object | Document | string} result.data.transaction - Custom data can be returned here. {Object} result.result (optional) {Boolean} result.result.success (optional)- It can be used to cause failure in generation. Useful when want to abort the generation process. Optional and defaulted to true if omitted. {string} result.result.eiAuditTrailMsg (optional)- This appears on the E-Document Audit Trail of transaction. |

##### EI PEPPOL Tax Category Custom Record {#subsect_0310124243}

The EI PEPPOL Tax Category custom record consists of tax details which can be used in e-document generation with Version 2 Avalara templates. To access the custom record, go to Customization > Lists, Records & Fields > Record Types > Find 'EI PEPPOL Tax Category' > List.

<a id="table_0310124821"></a>

| Field Name | Description |
| --- | --- |
| EI PEPPOL Tax Category Code | This field consists of the PEPPOL Tax Category Code |
| Tax Exemption Reason | This field provides the reason for the tax exemption applied to this record. |
| Tax Exemption Code | This field stores the list of VATEX codes with its code, title and description. |

The **Tax Exemption Reason** and **Tax Exemption Code** fields will be visible and editable only when the EI PEPPOL TAX Category Code is one of the below:

-   E- Exempt for VAT
    
-   AE- Reverse Charge
    
-   K- Intra - community supply
    
-   O- Not subject to VAT
    
-   G- Export outside EU
    

Important:

Create a new instance whenever you want to use tax exemption details as each bundle update overwrites the existing 12 instances.

To use exempt tax category codes with tax exemption details, create a new instance of the EI PEPPOL tax category code and assign it to a tax code record. Then use this tax code in the transaction to ensure the generated e-document includes the tax exemption details. The system will include the tax exemption details in the generated e-document only if you select the **Apply Validations** box on the e-document template.

###### Payment Means and Third- Party Sourcing {#subsect_0617100018}

This section explains how Payment Means values and third-party reference information are sourced and populated in the generated XML.

1.  Sourcing from ALF Third Party References:
    
    -   If multiple third-party entities with the same role are attached to a transaction, the system uses the first entity encountered. The generated XML includes information from that entity by default.
        
    -   In SuiteTax accounts, if the entity assigned as the Tax Representative Party under ALF Third Party does not have a default tax registration number, the system uses the first available tax registration record. The generated XML includes that tax registration number by default.
        
2.  Registering Payment Means Codes in the UMA SuiteApp:
    
    The process for registering payment means codes depends on the installation order of UMA and Electronic Invoicing (EI) SuiteApps.
    
    -   If UMA is installed before EI:
        
        Payment means codes are registered automatically in the UMA custom record during the EI installation process.
        
    -   If EI is installed before UMA:
        
        Go to Customization> Scripting >Script Deployment, and invoke a Suitelet with deployment id 'customdeploy\_ei\_uma\_map\_inst\_service\_su ' to register payment means code in UMA custom record.
        
3.  Sourcing from ALF and UMA SuiteApps:
    
    For the Payment Means tag to be generated, the ALF Method of Payment used in the transaction must be mapped to the corresponding Payment Means Code provided by the UMA SuiteApp.
    
    #### To configure the mapping:
    
    1.  Go to Setup > Universal Mapping Assistant > Mapping Setup.
        
    2.  In the **Mapping Type** field, select **Methods of Payment**.
        
    3.  In the **Payment Method Standard** field, select **Peppol-81**.
        
    4.  Click **Search**.
        
    5.  The list of available payment method mappings is displayed. Ensure that the ALF Method of Payment used in the transaction is mapped to the appropriate Payment Means Code.
        
    
    If the required mapping is not available, the Payment Means tag will not be generated in the output.
